编译器常被画成一条流水线，但“依次调用几个模块”不是它最重要的性质。更准确的说法是：编译器反复改变程序的表示，同时尽量保留源程序的含义。

对一个 pp 表达式 `a + b`，源码字符、token、AST、单态化 AST 和 LLVM 指令长得完全不同；如果 `a`、`b` 是 `u32`，最终却生成 `sdiv`，翻译在语法上成功了，语义上却失败了。

## 三种互补视角

PLAI 强调“通过实现来理解语言”。先写一种最小表示，再让表示随语言特性增长。pplc 的 `Expr`、`Stmt` 和 `Item` 正是这种可执行的语言定义。

TAPL 给出另一条约束：静态类型判断应保证运行时不会进入某些无意义状态。pplc 不做形式化证明，但会把判断写成代码。例如条件必须是 `bool`，和类型的 `switch` 必须穷尽，泛型模板不能偷偷对未知 `T` 使用 `+`。

龙书则提供工程分层：词法分析识别 token，语法分析构造树，语义分析处理上下文相关约束，后端生成中间表示和目标程序。pplc 沿用这条主干，但根据项目规模合并了一些工业编译器常见层次。

## pplc 的不变量

每个阶段都应建立一个比前一阶段更强的不变量：

| 阶段 | 输入 | 输出保证 |
|---|---|---|
| lexer | Unicode 字符 | token 有种类和起始行列 |
| parser | token | AST 结构满足 pp 文法 |
| import | 多个 AST | 去重后的扁平 item 集合 |
| mono | 含模板的 AST | 被使用的泛型实例已具体化 |
| sema | 具体 AST | 名称、类型、作用域、分支约束成立 |
| codegen | 已检查 AST | LLVM module 表达同一程序 |
| LLVM/链接器 | module | 可执行代码或目标文件 |

当前实现中 `mono` 在完整 `sema` 前运行，所以泛型模块内部还有一组模板级验证。这个次序不是普遍定律，而是显式类型参数 + AST 单态化设计的结果。后文会专门分析它。

## “正确”有几层

编译器正确性至少包括四层：

1. 接受所有应接受的 v0.3 程序；
2. 拒绝所有规范明确禁止的程序；
3. 生成结构合法的 LLVM IR；
4. 生成程序的可观察行为与源语言语义一致。

只测 `fib.pp` 的返回值只能覆盖第四层的一小角。pplc 的测试因此同时检查成功运行、错误诊断和具体 IR 指令，例如无符号除法必须出现 `udiv`。

这也是本课程的主线：每引入一个编译阶段，都要问它建立了什么不变量、错误应该在哪一层暴露、测试怎样观察这个承诺。
