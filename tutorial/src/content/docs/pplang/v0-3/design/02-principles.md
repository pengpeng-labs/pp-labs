pplang 不直接复制教材中的语言，也不按流行语言的功能表挑选语法。它从几个稳定的理论问题出发，再根据系统工程的约束作出较小的选择。

## 原则一：类型必须排除无意义状态

TAPL 把类型系统看作对程序行为的静态分类。工程上最直接的落点不是写出复杂推导规则，而是让错误状态无法自然表达。

```pp
enum ParseResult {
    Ok(int),
    Error(str),
}
```

`ParseResult.Ok` 才携带结果，`ParseResult.Error` 才携带消息。相比 `status + value + error` 三个互相独立的字段，enum 把 tag 和合法 payload 绑定起来；穷尽 switch 让新增状态不能被旧代码静默忽略。

同一个原则还体现在：

- `bool` 不接受任意整数，条件必须确实是逻辑值。
- `str` 绑定地址和长度，避免把范围信息留在另一个变量中。
- struct 绑定一组同时存在的字段，tuple 只承担短期匿名组合。
- 泛型实例是具体名义类型，`Option[int]` 与 `Option[str]` 不混用。

## 原则二：语义必须能沿实现路径解释

PLAI 强调通过实现理解语言。pplang 因而偏好一条可追踪的语义路径：

```text
源代码 → AST → 类型检查 → 单态化 → LLVM IR
```

struct 方法只是普通函数的调用糖；`for` 可以降为明确循环；enum 是 tag 加 payload storage；泛型通过具体类型实例化。语法可以改善表达，但不能掩盖一个无法说明的运行时机制。

这不意味着所有实现都简单，而是每个机制都能在 pplc 中指出负责的模块、静态检查和最终表示。

## 原则三：数据表示属于语言教育的一部分

CSAPP 和计算机组成原理提醒我们：类型最终要占据字节、寄存器和地址。pplang 因而不会把内存模型完全藏在运行时后面。

| 表面类型 | 工程表示 | 程序责任 |
|---|---|---|
| `int` | 32 位有符号整数 | 理解溢出与有符号比较 |
| `u8...u64` | 对应位宽无符号整数 | 用于字节、掩码、地址通道 |
| `str` | `{ptr,len}` | 保证所指内存在视图使用期有效 |
| `[N]T` | 连续定长元素 | 长度属于类型与布局 |
| `*T` | 裸地址 | 保证地址、对齐和生命周期合法 |
| enum | `i32 tag + payload` | 不跨未知 extern ABI 猜布局 |

这也是教程会反复使用 `pp ir` 的原因：高级语义和机器表示不能永远分开讲。

## 原则四：关键能力必须显式

对未知类型 `T`，编译器不会假设它支持 `<`：

```pp
fn larger[T](a: T, b: T, less: fn(T, T) -> bool) -> T {
    if (less(a, b)) { return b; }
    return a;
}
```

这里的 `less` 既是普通值，也是泛型约束。调用点能直接看到使用了哪个比较规则，编译器不需要 trait 查找或约束求解。

显式还体现在 allocator、FFI 长度参数、整数转换和系统 builtin。pplang 不以“聪明推断最少代码”为首要目标，而以“关键事实能够局部读出”为目标。

## 原则五：机制少，但承诺必须完整

小语言不能以“小”为理由留下半套语义：

- 有无符号整数，就必须使用无符号除法、余数和顺序比较。
- 有词法作用域，就必须正确处理 shadowing 和 block 退出。
- 有切片，就必须兑现边界检查和 O(1) 长度。
- 有 Sum Type，就必须检查 payload 和穷尽性。
- 有泛型，就必须检查模板、去重实例并阻止无限实例化。

ppdb 与 ppos 不是装饰性的案例，而是这些承诺的长期回归集。

:::note[我们的观察]
“显式”不是把所有细节推给用户，“小”也不是少做检查。pplang 选择把有限信息组织得更紧，同时让真正危险的地址和资源责任保持可见。
:::
