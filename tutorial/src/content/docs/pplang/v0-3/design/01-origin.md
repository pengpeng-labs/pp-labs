pp 不是先画出语法，再寻找能展示它的程序。顺序恰好相反：我们想用一门足够小的语言讲清编译器，并让同一门语言真正写出数据库和操作系统。pp-os 与 pp-db 因而不是完成后的 demo，而是语言的压力测试。

## 三个目标必须同时成立

### 能教

读者应当能从 token、AST 一直追到 LLVM IR，而不是在宏展开、隐式推导和庞大运行时里迷路。语言的主要机制必须能够用一两个编译器模块解释。

### 能写系统软件

教学语言如果只能计算 Fibonacci，很难解释 ABI、内存、设备和存储。pp 必须能生成目标文件和 freestanding ELF，必须能表达裸指针、volatile、函数指针和外部符号。

### 能被 LLM 稳定生成

LLM 友好不是减少关键字，而是减少隐含上下文。同一段代码不应依赖复杂的候选集、trait 求解或生命周期推导才能知道含义。显式类型参数、严格 bool 和有限的控制流，让错误更早、更局部。

## 真实需求怎样塑造语言

ppdb 需要表示“一个值可能是整数、文本、布尔或空”。手写 `tag + fields` 不能保证 tag 与 payload 匹配，于是 v0.2 引入 enum、单层 payload 解构与穷尽 switch。

ppos 和协议栈反复处理带长度的字节数据。NUL 结尾字符串无法表示任意二进制，也让长度计算变成扫描，于是 `str` 收敛为 `{ptr,len}` 视图，并为切片增加运行时边界检查。

标准库与系统代码出现大量“同一种算法，只差元素类型”的重复。v0.3 因而加入显式单态化泛型；但比较、哈希、分配等能力仍通过函数指针传入，没有引入 trait 系统。

这形成 pp 的基本方法：先让真实程序暴露重复和风险，再加入能够消除它们的最小机制。

## 不是生产语言竞赛

pp 不试图在功能数量上追赶 Rust、Zig 或 C++。它的价值在于边界清楚：一名读者能够理解语言表面、编译器实现和系统程序之间的完整联系。
