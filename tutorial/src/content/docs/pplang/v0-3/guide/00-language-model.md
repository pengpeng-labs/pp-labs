学习一门语言很容易退化为记关键字。PLAI 和 TAPL 提供了更稳定的观察框架：一门语言至少要说明程序长什么样、程序怎样求值、哪些程序应在运行前被拒绝，以及这些规则怎样被实现。

## 四个不能混淆的层次

| 层次 | 回答的问题 | pplang 中的权威位置 |
|---|---|---|
| 具体语法 | 源码怎样写 | lexer、parser、EBNF |
| 抽象语法 | 程序由哪些结构组成 | pplc AST |
| 静态语义 | 哪些程序在运行前合法 | 类型、名字、作用域、穷尽检查 |
| 动态语义 | 合法程序运行时做什么 | 求值顺序、控制流、调用、内存操作 |

编译器和 JIT 是这些规则的一种实现。LLVM IR 是实现路径上的中间表示，不是 pplang 语义本身。

## 从字符到抽象语法

看这段代码：

```pp
let total: int = 1 + 2 * 3;
```

源码首先被拆成 token：

```text
let  total  :  int  =  1  +  2  *  3  ;
```

parser 再根据优先级构造结构。抽象语法关心的是：

```text
Let total : int
  Add
    Int(1)
    Mul
      Int(2)
      Int(3)
```

括号、空白和分号帮助人和 parser 识别结构，但 AST 不必原样保存所有表面符号。PLAI 从“怎样表示程序”开始，是因为没有抽象表示，就无法精确定义求值器、类型检查器或变换。

## 求值不是“编译器随便生成代码”

对上面的表达式，可以用小步直觉描述：

```text
1 + 2 * 3
→ 1 + 6
→ 7
```

pplang 还规定操作数和函数实参从左到右求值。这个规则在纯整数表达式中不显眼，一旦表达式包含函数调用、IO 或状态修改，就会影响可观察结果。

PLAI 训练读者在纸上模拟 evaluator：当前表达式是什么、名字环境是什么、下一步状态是什么。本教程不会为完整 pplang 写一套形式化解释器，但会沿用这种提问方式分析控制流、函数、defer 和 switch。

## 环境赋予名字含义

```pp
let value: int = 1;
if (true) {
    let value: int = 2;
    println("inner");
}
return value;
```

名字 `value` 本身没有固定含义。它由当前词法环境决定：

```text
外层环境: value ↦ 外层 int 绑定
  内层环境: value ↦ 内层 int 绑定
```

进入 block 扩展环境，离开 block 恢复外层环境。PLAI 的 static scoping 解释“名字指向哪个绑定”，pplc 的作用域栈则把这个模型落实成算法。

## 类型判断是另一套关系

TAPL 常把类型判断写成：

```text
Γ ⊢ e : T
```

读作：“在类型环境 Γ 下，表达式 e 具有类型 T。”例如加法的直觉规则是：

```text
Γ ⊢ left : int    Γ ⊢ right : int
----------------------------------
       Γ ⊢ left + right : int
```

这不是 pplang 的源码语法，而是解释 sema 判断的工具。若一侧是 bool，前提不成立，整个加法就没有合法类型。

函数调用也可以这样理解：

```text
Γ ⊢ f : fn(int, int) -> bool
Γ ⊢ a : int
Γ ⊢ b : int
---------------------------------
Γ ⊢ f(a, b) : bool
```

编译器错误不是一组任意 if/else；它们是在指出某条判断规则的前提无法成立。

## progress 与 preservation 的直觉

TAPL 用两个性质解释类型安全：

- **Progress**：一个闭合、良类型的项要么已经是值，要么还能继续求值，而不是卡在“不知道怎么做”的状态。
- **Preservation**：一个良类型项求值一步后，类型不会无故改变。

对 pplang，可以把它们理解为设计检查表：

- `1 + true` 应在运行前拒绝，不能等 LLVM 猜怎么办。
- switch 取得 payload 后，payload 类型必须与对应变体一致。
- 泛型实例化后，所有操作都必须对具体类型有效。
- `if` 的条件必须是 bool，codegen 才有一致的分支输入。

但要把握边界：pplang v0.3 没有完成形式化证明，裸指针、extern 和目标 builtin 也能绕过普通内存安全。**类型安全不等于内存安全，更不等于整个系统无 bug。**

## 积类型与和类型

```pp
struct Point { x: int, y: int }
enum Result { Ok(int), Error(str) }
```

Point 是积类型：一个值同时包含 x 和 y。Result 是和类型：一个值只能属于 Ok 或 Error 中的一种情况。

```text
Point  ≈ int × int
Result ≈ int + str
```

这里的乘号与加号表示状态空间的组合方式。struct 容易产生“字段的所有组合”，enum 则用变体排除互斥状态的非法组合。后续章节会把这个理论直接用于 parser result、SQL value 和协议状态。

## 表面语法与核心机制

PLAI 用 desugaring 区分方便书写的表面形式与较小的核心语言。pplang 也有类似边界：

```pp
point.move_by(1, 2);
```

语义上等价于：

```pp
move_by(&point, 1, 2);
```

`for`、方法调用、tuple 解构和 defer 都改善书写体验，但不能引入无法解释的隐藏能力。pplc 不一定把每种形式机械地改写成另一段 pp AST；“脱糖”首先是一种理解语义的方法。

enum 则不是单纯语法糖，因为它同时引入名义类型、payload 检查、穷尽性和运行时 tag 表示。

## 规范、教程和实现的职责

```text
规范：规定什么是合法程序，以及合法程序可观察到什么
教程：建立理解，解释设计与使用方法
pplc：实现规范，并通过测试证明一致性
```

不要从当前 LLVM IR 的偶然形状反推永恒语言规则，也不要因为教程省略了边角情况就按 Rust、C 或 Go 类推。最终裁决者是 v0.3 规范。

3. 写出 `fn(int) -> bool` 调用的类型判断前提。
4. 分别用 struct 和 enum 表示“解析成功或失败”，列出 struct 允许但没有意义的状态。
5. 找出 pplang 中三个语法糖，并说出其核心机制。
